title: 秋招 OS｜Playwright 投递自动化设计
---

# 1. 目标

Browser Automation 的目标：

> 帮用户减少重复填写招聘申请表的工作量。

不是：

> 完全无人值守自动投递。

------------------------------------------------------------------------

# 2. 核心流程

``` text
用户选择岗位
      ↓
创建 Application
      ↓
点击“开始准备投递”
      ↓
Playwright 打开招聘网页
      ↓
检查登录状态
      ↓
未登录？
      ↓
用户自己登录
      ↓
继续
      ↓
识别申请表
      ↓
提取字段
      ↓
字段映射
      ↓
填写普通信息
      ↓
敏感信息留空
      ↓
暂停
      ↓
用户检查
      ↓
用户自己完成最终提交
      ↓
系统标记已投递
```

------------------------------------------------------------------------

# 3. 浏览器模式

第一版建议使用：

> 本地浏览器

而不是服务器远程浏览器。

好处：

-   用户可以直接看到页面
-   登录简单
-   验证码由用户处理
-   MFA 由用户处理
-   最终提交由用户完成

------------------------------------------------------------------------

# 4. 登录

第一次：

``` text
打开招聘网站
↓
用户登录
↓
用户完成验证码
↓
用户完成 MFA
↓
保存认证状态
```

以后：

``` text
打开浏览器
↓
复用认证状态
```

------------------------------------------------------------------------

# 5. 登录态安全

登录状态：

-   只保存本地
-   不提交 Git
-   不进入数据库
-   不发送给 DeepSeek
-   不记录到普通日志

------------------------------------------------------------------------

# 6. 页面识别

进入申请页面后：

Playwright 获取：

-   input
-   textarea
-   select
-   checkbox
-   radio
-   label
-   placeholder

形成：

``` json
{
  "label": "最高学历",
  "type": "select",
  "required": true
}
```

------------------------------------------------------------------------

# 7. 字段映射

字段映射由：

> 规则 + DeepSeek

共同完成。

优先规则。

例如：

``` text
手机号
→ phone

邮箱
→ email

姓名
→ name

学校
→ education.school
```

无法确定时才询问 DeepSeek。

------------------------------------------------------------------------

# 8. 敏感字段

以下字段必须自动跳过：

``` text
身份证号
护照号
银行卡
密码
验证码
短信验证码
邮箱验证码
MFA
人脸识别
```

例如：

``` json
{
  "label": "身份证号码",
  "action": "SKIP",
  "reason": "sensitive"
}
```

------------------------------------------------------------------------

# 9. 用户手动接管

页面显示：

> 已自动填写 28 项信息。

> 有 3 项需要你手动填写。

例如：

``` text
身份证号码
验证码
紧急联系人
```

用户填写完成后：

> \[继续\]

------------------------------------------------------------------------

# 10. 最终提交

这是绝对的人工作业步骤。

系统可以：

-   打开最终申请页面
-   滚动到提交按钮
-   提醒用户检查

但：

> **系统不点击最终提交按钮。**

用户自己点击。

然后回到秋招 OS：

> \[已完成投递\]

------------------------------------------------------------------------

# 11. Application 状态

``` text
PREPARING
    ↓
LOGIN_REQUIRED
    ↓
FORM_ANALYZING
    ↓
FORM_FILLING
    ↓
WAITING_USER
    ↓
READY_TO_SUBMIT
    ↓
SUBMITTED
```

异常：

``` text
FAILED
BLOCKED
```

------------------------------------------------------------------------

# 12. 可恢复

如果浏览器关闭：

不要直接丢任务。

保存：

``` text
application_id
browser_task_id
current_url
current_step
status
```

重新启动后允许：

> \[继续投递准备\]

------------------------------------------------------------------------

# 13. 日志

记录：

``` text
开始时间
结束时间
当前 URL
当前步骤
字段数量
自动填写数量
跳过数量
异常信息
```

不要记录：

-   密码
-   身份证
-   验证码
-   Cookie
-   完整登录态

------------------------------------------------------------------------

# 14. 网站适配

不同招聘网站页面结构不同。

不要写一个巨大的万能脚本。

建议：

``` text
browser/
├── common/
│   ├── field_extractor
│   ├── field_mapper
│   └── browser_manager
│
├── sites/
│   ├── boss/
│   ├── official/
│   └── ...
```

网站专用逻辑只处理该网站特有的页面结构。

------------------------------------------------------------------------

# 15. 第一版实现策略

不要一开始支持所有招聘网站。

建议先实现：

1.  一个公司官方招聘网站
2.  BOSS 一个典型流程

跑通：

``` text
登录
→
打开职位
→
识别表单
→
填写普通信息
→
跳过敏感信息
→
人工接管
→
最终提交
```

之后再扩展。

------------------------------------------------------------------------

# 16. 重要边界

Browser Automation 必须遵守：

-   不绕过验证码
-   不绕过风控
-   不绕过登录限制
-   不自动获取短信验证码
-   不自动处理人脸验证
-   不自动提交求职申请

如果网站阻止自动化：

> 停止并交给用户。

------------------------------------------------------------------------

# 17. 最终体验

用户理想体验：

``` text
岗位车
↓
选择岗位
↓
准备投递
↓
浏览器自动打开
↓
用户登录（第一次）
↓
AI 自动填写
↓
“身份证需要你填写”
↓
用户填写
↓
“请检查申请内容”
↓
用户检查
↓
用户点击招聘网站提交
↓
回到秋招 OS
↓
点击“已完成投递”
```

整个过程的目标：

> **让用户从"手动填写几十分钟"变成"AI 填大部分 + 用户检查几分钟"。**
